# Архитектурные паттерны и паттерны устойчивости

В данном документе приведено обоснование выбора и реализации паттернов в рамках Highload PoC.

## 🏗 Паттерны проектирования (Design Patterns)

### 1. API Gateway (Traefik)
*   **Зачем**: Обеспечивает единую точку входа (порт 80), скрывая внутреннюю топологию микросервисов. Позволяет централизованно управлять SSL, сжатием (Gzip) и сквозной авторизацией.
*   **Реализация**: Настроен через динамическую конфигурацию [traefik_dynamic.yaml](../traefik_dynamic.yaml).
*   **Выгода**: Снижение сложности клиентского кода и возможность горизонтального масштабирования бэкендов за шлюзом.

### 2. Transactional Outbox
*   **Зачем**: Решает проблему распределенной транзакции между БД и Брокером Сообщений (NATS). Гарантирует, что событие об оформлении заказа будет доставлено хотя бы один раз (at-least-once), даже если брокер временно недоступен.
*   **Реализация**: [outbox.go](../services/order/internal/app/outbox.go). События сохраняются в таблицу `outbox_events` в той же транзакции, что и заказ. Отдельный Relay-воркер перекладывает их в NATS.
*   **Выгода**: Исключение несогласованности данных (Data Inconsistency) между сервисами Заказов и Платежей.

## 🛡 Паттерны устойчивости (Resilience Patterns)

### 1. Circuit Breaker (Предохранитель)
*   **Зачем**: Предотвращает каскадные сбои при интеграции с внешним PSP (Payment Service Provider). Если PSP начинает отвечать ошибками, предохранитель "размыкается", мгновенно возвращая ошибку клиенту без попытки отправить запрос во внешнюю систему.
*   **Реализация**: [handler.go](../services/payment/internal/delivery/http/handler.go#L126).
*   **Выгода**: Снижение нагрузки на неисправную систему и предотвращение "зависания" наших горутин в ожидании таймаута внешнего сервиса.

### 2. Rate Limiting (Ограничение частоты)
*   **Зачем**: Защищает систему от DDoS-атак и лавинообразной нагрузки (Retry Storms). 
*   **Реализация**: Настроено на уровне шлюза в [traefik_dynamic.yaml](../traefik_dynamic.yaml#L31). Разные лимиты для чтения (1000 RPS) и записи (100 RPS).
*   **Выгода**: Система остается отзывчивой для большинства пользователей даже при аномальных всплесках трафика.

### 3. Bulkhead (Перегородки)
*   **Зачем**: Изолирует ресурсы внутри одного сервиса. В нашем случае, тяжелые поисковые запросы не могут занять более 100 одновременных потоков.
*   **Реализация**: [handler.go](../services/catalog/internal/delivery/http/handler.go#L127) (через Go Semaphores).
*   **Выгода**: Если поиск начнет тормозить, сервис всё равно сможет показывать страницы ресторанов и меню, так как для них ресурсы выделены отдельно.

### 4. Timeout (Таймаут)
*   **Зачем**: Гарантирует "быстрый отказ". Запрос не должен висеть вечно, потребляя ресурсы.
*   **Реализация**: Установлены жесткие лимиты (1s на поиск) в [search.go](../services/catalog/internal/repository/search.go#L60).
*   **Выгода**: Предотвращение исчерпания пула соединений БД и памяти сервера при медленных ответах.

### 5. Fallback (Запасной вариант)
*   **Зачем**: Обеспечивает "Graceful Degradation" (плавную деградацию). 
*   **Реализация**: [handler.go](../services/catalog/internal/delivery/http/handler.go#L145). Если поисковый движок Meilisearch недоступен, сервис возвращает пустой список результатов вместо 500 ошибки.
*   **Выгода**: Пользователь может продолжить работу с сайтом, даже если один из компонентов временно неисправен.

### 6. Retry with Backoff (Повторные попытки)
*   **Зачем**: Сглаживает кратковременные сетевые сбои.
*   **Реализация**: [resilience.go](../internal/resilience/resilience.go#L22).
*   **Выгода**: Автоматическое восстановление обработки событий без вмешательства человека.
