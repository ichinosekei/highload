## Итерация 0: Baseline

### 0a. Локальный замер

**Окружение**: Локальная машина разработчика. k6 и Docker на одной машине.

**RED-метрики (от k6)**:
*   **Rate**: 188 req/s суммарно, 19.5 orders/s (целевые 30), ~64 search/s (целевые 100).
*   **Errors**: 0.007% — 6 из 79109 запросов (все 6 — `init_payment`, HTTP 429 Too Many Requests от Rate Limiter на шлюзе).
*   **Duration**: search p99 = 139ms, order p99 = 208ms, payment p99 = 37ms (p95).
*   Зафиксировано **89 dropped iterations** — k6 не успевал создать нужное количество VU-итераций.

**USE-метрики (от docker stats, 5-я минута)**:
*   **Utilization**: CPU суммарный ~10%. Gateway 9.43%, Catalog 4.39%, Postgres 3.11%.
*   **Saturation**: Gateway RAM **95.5%** (95.49MiB / 100MiB) — критический уровень, близок к OOM.
*   **Errors**: 6 ошибок `init_payment` — HTTP 429 Too Many Requests. Rate Limiter на шлюзе отклонял запросы при нехватке памяти для обработки входящих соединений.

**Анализ**:
*   Система держит нагрузку на чтение, но проседает на записи (**19.5 RPS** при целевых 30).
*   **Узкое место**: Лимит памяти шлюза Traefik (100MB). При нагрузке потребление достигает 95%, что ограничивает количество одновременных соединений и ведет к отбросу итераций.
*   CPU загружен всего на ~10% — ресурс процессора используется неэффективно. Система «задыхается» по памяти шлюза, а не по вычислениям.

---

### 0b. Замер на VM

**Окружение**: VM (2 vCPU / 8 GB RAM / HDD). k6 запущен с ноутбука разработчика, трафик идет по сети до VM.

**RED-метрики (от k6)**:
*   **Rate**: 188.7 req/s суммарно, 19.57 orders/s, ~65 search/s.
*   **Errors**: 0.001% — 1 из 79256 (`create_order`).
*   **Duration**: search p99 = **51.81ms**, order p99 = **55.59ms**, payment avg = 8.27ms.
*   Зафиксировано **29 dropped iterations** (улучшение по сравнению с локальным: 89 → 29).

**USE-метрики (от docker stats, 5-я минута)**:
*   **Utilization**: CPU суммарный ~20%. Gateway 6.99%, Catalog 3.73%, Postgres 2.70%.
*   **Saturation**: Gateway RAM **59.1%** (59.1MiB / 100MiB) — лучше, чем локально, но всё ещё высокое.
*   **Errors**: 1 ошибка `create_order`.
*   Block I/O: Postgres 16.8MB write (HDD — потенциальное узкое место при росте нагрузки).

**Анализ**:
*   Latency на VM **существенно ниже**, чем локально (p99: 51ms vs 139ms для search, 55ms vs 208ms для order). Это парадоксально, но объясняется тем, что на локальной машине k6 и Docker конкурируют за CPU, а на VM сервисы работают без конкуренции с генератором нагрузки.
*   RPS на запись по-прежнему **~19.5**, что ниже целевых 30.
*   Gateway RAM снизилась (59% vs 95%), но остается ведущим bottleneck — это единственный контейнер с непропорционально высоким потреблением RAM.
*   CPU загружен всего на ~20% (суммарно) — система далека от предела вычислительных ресурсов. Нужно либо масштабировать сервисы, либо увеличить RPS на генераторе.

## Итерация 1: Оптимизация ресурсов и горизонтальное масштабирование

**Гипотеза**: Увеличение лимитов памяти шлюза, отключение access-логов и горизонтальное масштабирование сервисов позволит:
1. Устранить «бутылочное горлышко» по памяти Gateway.
2. Распределить нагрузку на оба vCPU.
3. Достичь целевых 30 RPS на запись и 100 RPS на чтение.

**Что сделано**:
1. Gateway: лимит памяти 100MB → 256MB, CPU 0.1 → 0.2.
2. Gateway: отключен `--accesslog` (каждая запись лога буферизуется в RAM; при 188 req/s это существенная нагрузка на память).
3. Горизонтальное масштабирование: запуск через `docker-compose.scaled.yaml` — 2 реплики для `catalog`, `order`, `payment`, `notification`.

**Результаты** (замер на VM, scaled mode):

**RED-метрики (от k6)**:
*   **Rate**: 188.6 req/s суммарно, 19.56 orders/s (средняя за 7 мин, включая ramp-up/down).
*   **Errors**: 0.003% — 3 из 79263 (все 3 — `search`, не `order`/`payment`).
*   **Duration**: search p99 = **14.84ms** (было 51ms), order p99 = **43.34ms** (было 55ms).
*   Dropped iterations: **28** (из ~8250 запланированных — **0.34%**, пренебрежимо мало).
*   ⚠️ Outliers: `order max=16.05s`, `search max=16.04s` — подозрительно на timeout Postgres.

**USE-метрики (от docker stats, 5-я минута)**:
*   **Utilization**: CPU суммарный ~25%. Нагрузка распределена по 2 репликам каждого сервиса.
*   **Saturation**: Gateway RAM **21.8%** (55.82MiB / 256MiB) — ✅ проблема полностью решена.
*   **Errors**: 3 ошибки на search (не критично).
*   Postgres: CPU 3.53%, RAM 80.72MiB / 1.5GiB, Block I/O 18.5MB write.

**Анализ**:
*   **Gateway bottleneck устранён**: RAM снизилась с 59% до 21.8% благодаря увеличению лимита и отключению access-логов.
*   **Latency значительно улучшилась**: search p99 упала в 3.5 раза (51→14ms), order p99 — на 22% (55→43ms).
*   **NFR фактически достигнуты**: k6 использует `ramping-arrival-rate`, который рампит нагрузку 5→15→30→0 iter/s. Средний 19.5/s — это математическое среднее по 7 минутам, а не потолок системы. Из ~8250 запланированных итераций отброшено лишь 28 (0.34%), что подтверждает, что пиковые 30 RPS на запись система обрабатывает.
*   **Новая проблема**: Единичные outliers с max latency ~16s. Вероятная причина — медленные запросы к Postgres на HDD при конкуренции за I/O. Это цель для Iteration 2.

## Итерация 2: Оптимизация базы данных

**Гипотеза**: Экстремальные outliers (max 16s) вызваны медленными запросами к Postgres, усиленными работой на HDD. Добавление индексов и тюнинг Postgres снизит max-latency и устранит оставшиеся ошибки.

**Что планируется сделать**:
1. Проверить наличие индексов на часто используемые поля (`orders.id`, `orders.restaurant_id`, `menu_items.restaurant_id`).
2. Настроить `shared_buffers` и `work_mem` в Postgres для кэширования данных в памяти.
3. Перезамер на VM.
