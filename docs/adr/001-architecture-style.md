# ADR-001: Выбор архитектурного стиля

## Статус
Принято

## Контекст
Проектируется сервис доставки еды для РФ + СНГ (5–20 млн MAU). Ключевые ограничения:
- **Ограниченный бюджет** и **маленькая команда** → нужна простая, реализуемая архитектура.
- **Разная критичность доменов**: платежи (99.99%) vs. каталог (99.90%) vs. уведомления (99.50%).
- **Изоляция контуров**: при деградации поиска платежи должны продолжать работать.
- **Масштабируемость x2 MAU за 12–18 месяцев** без пересборки.
- Пиковая нагрузка: 10k RPS (поиск), 500 RPS (создание заказов), 200 RPS (платежи).

## Альтернативы

### 1. Layered Monolith (слоистая монолитная)
- **Плюсы**: просто разрабатывать и деплоить, одна кодовая база, дешёвый старт.
- **Минусы**: невозможно масштабировать read-path (поиск, 10k RPS) отдельно от write-path (платежи). Отказ в одном модуле роняет всё. Невозможно обеспечить разные SLA для разных доменов.

### 2. Microservices (MSA)
- **Плюсы**: максимальная изоляция, независимый деплой и масштабирование.
- **Минусы**: взрывная операционная сложность (service mesh, distributed tracing, saga orchestration). Маленькая команда не потянет 8–10 отдельных пайплайнов. Значительные накладные расходы на инфраструктуру.

### 3. Service-Based Architecture (SBA) — **выбрано**
- **Плюсы**: 3–4 крупных сервиса вместо десятков → каждый сервис покрывает один бизнес-домен, при этом команда справляется с деплоем. Изоляция критичных контуров (платежи отдельно от каталога). Горизонтальное масштабирование по сервисам. Можно использовать разные БД для разных сервисов.
- **Минусы**: границы сервисов требуют аккуратного проектирования. Нужна асинхронная коммуникация между доменами.

## Решение
**Service-Based Architecture (SBA)** с элементами Event-Driven (асинхронная коммуникация через брокер сообщений для уведомлений и обновления статусов).

Выбор обусловлен:
1. SBA — оптимальный баланс между простотой монолита и изоляцией микросервисов.
2. 3–4 сервиса реализуемы маленькой командой.
3. Критичный контур (Order + Payment) изолирован от read-heavy контура (Catalog + Search).
4. Асинхронные события через брокер обеспечивают decoupling уведомлений и трекинга.

## Последствия
- **Положительные**: изоляция отказов между доменами; независимое масштабирование read/write; посильная операционная нагрузка.
- **Отрицательные**: нужен брокер сообщений (Kafka/RabbitMQ) → дополнительная инфраструктура; межсервисные вызовы добавляют latency; нужен transactional outbox для гарантии at-least-once delivery.
