# ADR-002: Выбор баз данных

## Статус
Принято

## Контекст
Система имеет принципиально разные паттерны доступа к данным:
- **Заказы и платежи**: write-heavy, ACID-транзакции обязательны, RPO=0, идемпотентность.
- **Каталог/меню**: read-heavy (до 6k RPS), редко обновляется, допускается eventual consistency.
- **Поиск**: полнотекстовый + фильтры (кухня, рейтинг, цена), до 10k RPS, допускается RPO 15 мин.
- **Корзина**: высокая частота записи/чтения (5k RPS), данные эфемерные, TTL-семантика.
- **Трекинг**: частые обновления статусов (2k RPS), быстрое чтение актуального состояния.

Объём данных за 3 года: ~260 GB ядро БД, ~1–2 TB с индексами и репликами.

## Альтернативы

### Вариант 1: Единая PostgreSQL для всего
- **Плюсы**: одна технология, простая эксплуатация.
- **Минусы**: PostgreSQL плохо подходит для полнотекстового поиска на 10k RPS. Корзина в SQL — избыточно для эфемерных данных. Единая БД = единая точка отказа, нарушает изоляцию контуров.

### Вариант 2: PostgreSQL + MongoDB + Elasticsearch + Redis
- **Плюсы**: каждая БД оптимальна для своего паттерна.
- **Минусы**: MongoDB не даёт преимуществ над PostgreSQL для каталога (структурированные данные, связи ресторан→блюда), добавляет ещё одну технологию для эксплуатации.

### Вариант 3: PostgreSQL + Elasticsearch + Redis — **выбрано**
- **Плюсы**: PostgreSQL — ACID для заказов/платежей и source of truth для каталога. Elasticsearch — полнотекстовый поиск + фильтры на 10k RPS. Redis — корзина (TTL), кэш меню, актуальные статусы трекинга. Три технологии вместо четырёх.
- **Минусы**: нужна синхронизация каталога PostgreSQL → Elasticsearch (CDC или периодическая). Redis как кэш требует стратегии инвалидации.

## Решение

| Хранилище | Технология | Обоснование |
|-----------|-----------|-------------|
| Заказы, платежи | **PostgreSQL** | ACID, RPO=0, идемпотентность через unique constraint на idempotency_key |
| Каталог (рестораны, меню) | **PostgreSQL** | Source of truth; структурированные данные со связями |
| Поисковый индекс | **Elasticsearch** | Полнотекстовый поиск + фасетная фильтрация, горизонтальное масштабирование, 10k RPS |
| Корзина, кэш меню, статусы трекинга | **Redis** | In-memory, TTL для корзины, sub-ms latency для трекинга, кэш горячих данных |
| Брокер сообщений | **Apache Kafka** | At-least-once delivery, ordering per partition, replay возможность |

## Последствия
- **Положительные**: каждое хранилище оптимизировано под свой паттерн доступа; изоляция — падение Elasticsearch не влияет на платежи; Redis разгружает PostgreSQL от read-нагрузки.
- **Отрицательные**: нужна синхронизация PostgreSQL → Elasticsearch (Debezium CDC или фоновый worker); три разных технологии хранения — больше операционной экспертизы; Redis не персистентный по умолчанию — для корзины это допустимо (эфемерные данные).
