# ADR-003: Гарантия надёжности платежей (Transactional Outbox + Idempotency)

## Статус
Принято

## Контекст
Платежи — самый критичный контур системы (99.99% availability, RPO=0). Требования:
- «Ничего не должно теряться» — платёжный статус всегда согласован с заказом.
- At-least-once delivery событий → нужна идемпотентность обработки.
- Внешний PSP присылает webhook-и, которые могут дублироваться или приходить с задержкой.
- При сбое между записью в БД и отправкой события в брокер — событие не должно теряться.

## Альтернативы

### 1. Dual Write (запись в БД + отправка в Kafka напрямую)
- **Плюсы**: простая реализация.
- **Минусы**: при сбое между записью в БД и отправкой в Kafka событие теряется. Нарушает гарантию «ничего не теряется». Невозможно обеспечить атомарность без 2PC.

### 2. 2PC (Two-Phase Commit) между PostgreSQL и Kafka
- **Плюсы**: теоретически атомарная запись.
- **Минусы**: Kafka не поддерживает XA/2PC. Высокая latency. Сложная реализация и эксплуатация. Не применимо на практике.

### 3. Transactional Outbox — **выбрано**
- **Плюсы**: событие записывается в таблицу `outbox` в той же транзакции, что и бизнес-данные → атомарность гарантирована средствами PostgreSQL. Отдельный relay-процесс (или Debezium CDC) вычитывает outbox и публикует в Kafka. At-least-once delivery + идемпотентность через `idempotency_key`.
- **Минусы**: дополнительная таблица в БД; relay-процесс добавляет задержку (обычно <100 ms); нужен механизм очистки outbox.

## Решение

1. **Transactional Outbox**: при создании заказа / обработке платежа — в одной PostgreSQL-транзакции записываются бизнес-данные и строка в таблицу `outbox_events`.
2. **Outbox Relay**: фоновый процесс (polling или CDC через Debezium) вычитывает новые события из `outbox_events` и публикует в Kafka.
3. **Idempotency Key**: каждая операция `create_order` и `confirm_payment` принимает `idempotency_key`. В БД — unique constraint. Повторный запрос с тем же ключом возвращает существующий результат.
4. **Webhook-и PSP**: обрабатываются идемпотентно по `payment_intent_id`. Дубли игнорируются.

## Последствия
- **Положительные**: гарантия «ничего не теряется» — событие не может потеряться между БД и брокером; идемпотентность защищает от дублей; паттерн хорошо документирован и проверен в индустрии.
- **Отрицательные**: дополнительная таблица `outbox_events` увеличивает нагрузку на БД; relay-процесс — дополнительный компонент для мониторинга; при сбое relay возможна задержка доставки событий (но не потеря).
