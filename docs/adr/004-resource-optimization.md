# ADR-004: Оптимизация под ограниченные ресурсы (2 vCPU, 8 GB RAM)

## Статус
Принято

## Контекст
Система должна быть развернута на одной виртуальной машине с жесткими лимитами:
- **CPU**: 2 vCPU
- **RAM**: 8 GB
- **Disk**: 72 GB HDD

На этапе проектирования были выбраны индустриально-стандартные технологии (Apache Kafka, Elasticsearch, Kong, 2 отдельных инстанса PostgreSQL). Однако анализ ресурсного бюджета показал, что этот стек **не поместится** в заданные рамки: JVM-компоненты (Kafka, Elasticsearch) суммарно потребляют 4–6 GB RAM только на себя, оставляя менее 2 GB на 4 Go-сервиса, Redis и операционную систему.

Задача — **заменить** тяжёлые компоненты на легковесные аналоги, сохранив при этом микросервисную архитектуру (SBA) и все ключевые гарантии (At-Least-Once, идемпотентность, изоляция контуров). Это позволит оптимизировать потребление ресурсов с заделом на будущее масштабирование.

## Решение

### 1. Замена брокера сообщений (Kafka → NATS JetStream)
- **Решение**: Использование **NATS JetStream** вместо Apache Kafka.
- **Обоснование**: NATS написан на Go, потребляет на порядок меньше памяти (<150 MB против 2+ GB у Kafka) и не требует JVM. Поддерживает персистентность и гарантии At-Least-Once, необходимые для надёжности платежей (НФТ-006).
- **Почему не оставили Kafka**: Kafka требует JVM, ZooKeeper/KRaft и значительный объём RAM даже в минимальной конфигурации. На HDD-диске её производительность деградирует из-за интенсивного I/O. Для нашего масштаба (200 RPS на платежи, 2k RPS на статусы) возможности Kafka избыточны.
- **При масштабировании**: Если в будущем нагрузка вырастет до уровня, где NATS станет узким местом, миграция на Kafka будет возможна, поскольку интерфейс Pub/Sub и паттерн Transactional Outbox остаются прежними — изменится только транспорт.

[Подробнее про возможности и сравнение с другими технологиями обмена сообщениями](https://docs.nats.io/nats-concepts/overview/compare-nats).

### 2. Замена поискового движка (Elasticsearch → Meilisearch)
- **Решение**: Использование **Meilisearch** вместо Elasticsearch.
- **Обоснование**: Meilisearch написан на Rust, потребляет значительно меньше RAM (500 MB–1 GB против 4+ GB у ES) при сопоставимой скорости поиска и фильтрации для каталога из 200k ресторанов.
- **Почему не оставили Elasticsearch**: ES — JVM-приложение. Даже с `-Xmx512m` оно использует значительно больше реальной памяти (off-heap, Lucene segments). Для нашего объёма данных (200k ресторанов, ~16 млн блюд) это overkill.
- **Альтернатива — PostgreSQL `pg_trgm`**: Рассматривался вариант полностью отказаться от выделенного поискового движка и использовать встроенные возможности PostgreSQL — расширение `pg_trgm` (триграммный поиск) в сочетании с GIN-индексами и полнотекстовым поиском (`tsvector`/`tsquery`). Это позволит сэкономить ещё 500 MB–1 GB RAM и убрать одну технологию из стека. Однако при росте каталога и усложнении поисковых сценариев (фасетные фильтры, typo-tolerance, ранжирование) PostgreSQL потребует значительно больше ручного тюнинга. Meilisearch выбран как компромисс: легче ES, но мощнее `pg_trgm` из коробки.

[Подробнее про возможности и сравнение с другими вариантами поисковых движков](https://www.meilisearch.com/docs/resources/comparisons/elasticsearch).

### 3. Консолидация СУБД (2x PostgreSQL → 1x PostgreSQL, Multi-DB)
- **Решение**: Использование **одного инстанса PostgreSQL 18**, обслуживающего несколько логических баз данных (`orders_db`, `catalog_db`).
- **Обоснование**: Каждый инстанс PostgreSQL — это набор фоновых процессов (WAL writer, autovacuum, checkpointer) и зарезервированная память (`shared_buffers`). Один инстанс с `shared_buffers = 1.5 GB` будет работать эффективнее, чем два по 512 MB. При этом **логическая изоляция данных сохраняется** — сервисы подключаются к разным базам данных и не имеют доступа к «чужим» таблицам (Database-per-service на уровне логики).
- **При масштабировании**: Разнесение на отдельные инстансы (или даже отдельные серверы) потребует только изменения connection string в конфигурации сервисов, без переработки кода.

### 4. Замена API Gateway (Kong → Traefik)
- **Решение**: Использование **Traefik Proxy (OSS)*.
- **Обоснование**: Написан на Go, потребляет ~50–100 MB RAM, имеет нативную интеграцию с Docker/K8s для автоматического обнаружения сервисов. Kong, в свою очередь, требует PostgreSQL для хранения конфигурации и значительно больше ресурсов.

## Ресурсный бюджет (прогноз)

| Компонент | Лимит RAM | Примечание |
|-----------|-----------|------------|
| ОС + Page Cache | ~3.5 GB | Критично для HDD — ОС кэширует горячие данные PG в памяти |
| PostgreSQL 18 | 1.5 GB | shared_buffers + work_mem, один инстанс, multi-DB |
| Meilisearch | 0.8 GB | Индекс 200k ресторанов + 16 млн блюд |
| Redis 7 | 0.4 GB | Корзины (TTL), кэш меню, трекинг |
| NATS JetStream | 0.15 GB | Брокер + персистентный storage |
| Traefik | 0.1 GB | Reverse proxy + routing |
| 4× Go Services | 1.2 GB | ~300 MB на сервис (с GOMEMLIMIT) |
| **Итого** | **~7.65 GB** | Запас ~350 MB |

## Последствия

### Положительные
- Все компоненты уместятся в 8 GB RAM, оставляя запас для Page Cache (критично для HDD).
- Zero-JVM стек: все компоненты написаны на Go, Rust или C — минимальный overhead, быстрый холодный старт.
- Микросервисная архитектура (SBA) полностью сохранена — при переезде на более мощное железо достаточно будет изменить конфигурацию, а не переписывать код.

### Отрицательные
- Meilisearch имеет меньше возможностей для сложной аналитики, чем Elasticsearch (но для задачи поиска по каталогу с фильтрами этого достаточно).
- NATS менее распространён в enterprise-среде, чем Kafka (но Go-библиотеки для NATS очень качественные и хорошо поддерживаются).
- Один инстанс PostgreSQL — единая точка отказа для БД (смягчается через streaming replication при наличии второй VM в будущем).
